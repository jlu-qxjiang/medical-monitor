## 2. 市场背景与问题定义

### 2.1 宏观数据

- 中国 60 岁以上人口 **2.97 亿**（国家统计局 2025 年数据），占总人口 21.1%
- 空巢老人占比超 **50%**，其中独居老人约 **4000 万**
- 慢性病老年人日均服药 **3-8 种**，用药依从率仅 **40%-55%**（WHO）
- 每年因用药错误导致的急诊住院中，**65 岁以上人群占 72%**
- 中国有 **2.2 亿**异地就业人口，其中约 **60%** 的父母在老家

### 2.2 核心痛点三角

```
                老人
               /    \
    记不住吃药时间   /      \  看不清说明书
    记不清吃没吃过  /        \  药名相近易混淆
                /          \
               /  用药安全危机 \
          子女                  医疗系统
    异地工作，打电话问          缺乏患者居家
   「吃药没」双方都烦            用药依从性数据
    出了事才知道漏服            复诊只能口头问
```

### 2.3 现有解决方案的致命缺陷

| 方案 | 问题 |
|------|------|
| **智能药盒硬件**（如 Hero 智能药盒、PillDrill） | 价格 200-800 元，需充电、需蓝牙配网，老人接受度极低 |
| **手机提醒 App** | 老人不用智能手机 App，提醒被淹没在通知栏里 |
| **子女打电话** | 不可持续，老人觉得被监视，子女工作忙容易忘 |
| **保姆/护工** | 成本高（月均 5000+），且无法监督用药质量 |

**核心洞察：市场需要一个零硬件成本、老人零学习成本、子女能实时感知的解决方案。**

## 3. 用户画像

### 3.1 Persona A：独居老人 张秀兰（目标使用者）

| 维度 | 描述 |
|------|------|
| 年龄 | 68 岁 |
| 居住地 | 四川成都（老家），女儿在上海 |
| 健康状况 | 高血压 10 年 + 2 型糖尿病 5 年 |
| 每日用药 | 早上：降压药（硝苯地平 1 粒）、降糖药（二甲双胍 1 粒）；中午：降糖药（阿卡波糖 1 粒）；晚上：降脂药（阿托伐他汀 1 粒）、阿司匹林 1 粒 |
| 手机使用习惯 | 会用微信发语音、刷视频号、抢红包，**不会安装 App** |
| 核心痛点 | 下午那顿降糖药经常忘；上周药吃完了才发现没买 |
| 典型一天 | 早上 6:30 起床 → 做早饭 → 吃药（经常配着早饭吃所以早上记得）→ 上午逛公园 → **中午 12 点那顿老是忘**（因为一个人吃午饭没有固定时间）→ 下午打麻将 → 晚上看电视吃药 |
| 心理诉求 | 「不想给女儿添麻烦，但一个人确实记不住那么多药」 |

### 3.2 Persona B：异地子女 李薇（主要使用者 / 付费决策者）

| 维度 | 描述 |
|------|------|
| 年龄 | 35 岁 |
| 工作地 | 上海，互联网公司产品运营 |
| 家庭状况 | 母亲张秀兰独居成都，自己是独生女 |
| 日常习惯 | 午饭休息时看一眼老家监控摄像头，晚上下班路上和妈妈打电话 |
| 核心痛点 | 妈妈有没有按时吃药？今天中午那顿吃了吗？药还剩多少？上次复诊医生说了啥？——这些信息全是盲区 |
| 焦虑峰值 | 下午 2 点给妈妈发微信「吃药了吗」没回复，开始脑补各种糟糕场景 |
| 心理诉求 | **愧疚感驱动**——自己没法在身边照顾，需要一个能代替自己提醒和确认的工具，让自己在远方也能「看到」妈妈的用药情况 |

### 3.3 Persona C：社区家庭医生 王晓明（潜在使用者）

| 维度 | 描述 |
|------|------|
| 年龄 | 42 岁 |
| 工作地 | 成都某社区卫生服务中心 |
| 签约患者 | 约 200 名慢性病老人，其中包括张秀兰 |
| 核心痛点 | 每次张秀兰来复诊，问「按时吃药了吗」都回答「吃了吃了」，但血糖数据波动很大，怀疑用药依从性差但没有客观证据 |
| 心理诉求 | 需要患者居家的真实用药数据来辅助用药方案调整 |

### 3.4 用户角色关系图

```
              ┌──────────┐
              │ 张秀兰    │ ← 使用者（吃药的人）
              │ (老人)    │
              └─────┬────┘
                    │ 母女关系
                    │
              ┌─────┴────┐      ┌──────────┐
              │ 李薇      │      │ 李强      │ ← 可能有多个子女
              │ (子女)    │──────│ (女婿)    │    共同监护
              └─────┬────┘      └──────────┘
                    │
                    │ 复诊时提供数据
                    ▼
              ┌──────────┐
              │ 王医生    │ ← 受益者（看用药数据）
              │ (社区医生)│
              └──────────┘
```

> **关键判断：付费方（子女）≠ 使用方（老人）。产品必须同时满足子女的「安心需求」和老人的「不被打扰的尊严」。**

| W5 | 语音助手交互 | 老人对着手机说话的习惯尚未建立，投入产出比低 |

## 6. 核心业务流程

### 6.1 首次设置流程（一次性）

```
子女打开小程序
  → 微信授权登录
  → 创建家庭组（生成唯一邀请码）
  → 通过微信转发邀请码给老人
  → 老人点击加入（无需手动输入邀请码）
  → 【子女端】录入药品：
      ├── 搜索药品模板库（快速选择常见药）
      ├── 拍照 OCR 识别（自动填充药名规格）
      └── 手动填写（兜底方案）
  → 设定用药计划：
      ├── 选择药品
      ├── 设定每日用药时间（如 08:00 / 12:30 / 18:00）
      ├── 设定每次剂量
      └── 设定药品初始余量
  → 【老人端】授权订阅消息
      → 引导页：展示一个模拟的「用药提醒消息」
      → 点击「去授权」按钮
      → 微信系统弹窗 → 用户确认
  → 设置完成
```

### 6.2 每日用药提醒流程（核心闭环）

```
═══════════════════════════════════════════════
  时间线: 以早上 8:00 为例
═══════════════════════════════════════════════

[07:59:00] 后端定时任务扫描 → 发现张秀兰 8:00 应服药
[08:00:00] 推送微信订阅消息 → 「降压药（硝苯地平）1粒 + 降糖药（二甲双胍）1粒」
[08:00:05] 张秀兰手机弹出微信服务通知
       ↓
    ┌──────────────────────────────────┐
    │       老人看到消息后的三个分支      │
    ├──────────────────────────────────┤
    │ ✅ 已服用 → 记录入库 → 余量-1     │
    │ ❌ 未服用 → 选择原因 → 通知子女    │
    │ ⏭️ 跳过   → 选择原因 → 通知子女    │
    └──────────────────────────────────┘
       ↓ 未做任何操作
[08:30:00] 超时 30min → 再次推送微信消息
            → 同时通知子女：⚠️ 母亲早上的降压药尚未确认
       ↓ 仍然未操作
[09:00:00] 超时 60min → 【短信】发送至老人手机
            → 通知子女：🔴 母亲早上的降压药已超时 1 小时
       ↓ 仍然未操作（高危）
[09:30:00] 超时 90min → 【语音电话】自动拨打张秀兰手机
            → 接通后播放：「您好，您的降压药和降糖药还没有服用，请及时吃药」
            → 通知子女：🚨 已触发语音电话提醒
```

### 6.3 异常分支

| 异常场景 | 处理方式 |
|----------|----------|
| **老人点错了（误点「已服用」）** | 确认后 5 分钟内可撤销，状态退回「待确认」 |
| **老人手机没电/关机** | 超时未确认正常走升级链路，子女手动打电话确认 |
| **微信订阅消息次数耗尽** | 系统检测授权状态，引导老人重新授权 |
| **网络故障** | 确认操作本地缓存，联网后自动补传 |
| **老人多次漏服（连续 3 天同一时段）** | 系统生成「漏服报告」推送给子女，建议关注 |
| **药品余量不足** | 子女端标黄预警（余量 ≤ 3 天），标红告警（余量 = 0） |

## 7. 验收标准

### 7.1 Must Have 功能验收标准

#### M1: 微信授权登录

- [ ] 用户点击「微信登录」→ 弹出微信授权 → 授权后自动完成登录
- [ ] 用户拒绝授权 → 停留在登录页，提示「需要授权才能使用」
- [ ] 已登录用户再次打开小程序 → 无需重新登录
- [ ] Token 过期后 → 自动刷新或引导重新登录

#### M2: 家庭组管理

- [ ] 创建家庭组后生成 6 位数字邀请码
- [ ] 被邀请人打开小程序 → 自动识别邀请参数 → 一键加入
- [ ] 同一个家庭组可以有多个「子女」角色
- [ ] 家庭组创建人具有「管理员」权限（可以移除成员）
- [ ] 一个用户可以属于多个家庭组（如同时是父母+岳父母的家庭组成员）

#### M3: 药品管理

- [ ] 子女可以手动录入药品：名称、规格（如 5mg×30片）、用法（如每日 3 次，每次 1 片）、初始余量
- [ ] 药品列表按药品名称排序
- [ ] 可以编辑已有药品信息
- [ ] 可以删除药品（已有用药计划的药品需先解除关联）

#### M4: 用药计划

- [ ] 设定每日用药时间点（如 08:00、12:30、18:00）
- [ ] 每个时间点可选择 1-N 种药品及每次剂量
- [ ] 支持修改和删除用药计划
- [ ] 修改计划后，当天的提醒按最新计划执行

#### M5: 定时提醒

- [ ] 在设定的时间点 ±1 分钟内推送微信订阅消息
- [ ] 消息内容包含：药品名称、剂量、当前时间点
- [ ] 消息可点击 → 跳转到确认页面
- [ ] 如果用户未授权订阅消息 → 引导授权

#### M6: 确认反馈

- [ ] 点击「已服用」→ 记录时间 → 显示「已确认」绿色状态 → 余量自动 -1
- [ ] 点击「未服用」→ 弹出原因选择（忘记 / 不舒服 / 药没了 / 其他）→ 记录状态
- [ ] 点击「跳过」→ 弹出原因选择（医生让停 / 今天外出 / 其他）→ 记录状态
- [ ] 已服用确认后 5 分钟内 → 可点击「撤销」→ 状态回退
- [ ] 按钮响应时间 ≤ 2 秒

#### M7: 实时看板

- [ ] 子女端首页展示家庭成员的今日用药状态卡片
- [ ] 已服用 = 绿色 ✅ / 等待中 = 黄色 ⏳ / 已超时 = 红色 🔴 / 未服用 = 灰色 ❌ / 跳过 = 蓝色 ⏭️
- [ ] 每个状态标签旁显示具体时间（如「08:03 已服用」）
- [ ] 切换查看不同家庭成员（如有多个老人）

#### M8: 超时告警

- [ ] 提醒发出 30 分钟后老人未确认 → 推送通知给所有子女端
- [ ] 提醒发出 60 分钟后仍然未确认 → 再次推送子女端（加重语气）
- [ ] 告警消息包含：哪位老人、什么药品、已超时多久
- [ ] 老人确认后 → 清除对应告警状态

#### M9: 用药计划修改

- [ ] 修改立即生效，不影响当天已过时间点
- [ ] 当天后续时间点的提醒按新计划执行
- [ ] 修改记录日志

## 8. 竞品分析

### 8.1 直接竞品

| 维度 | **智能药盒硬件**（Hero/PillDrill/忆捷） | **「吃药啦」小程序** | **小荷健康**（字节） | **「用药助手」**（丁香园） |
|------|------|------|------|------|
| **形态** | 硬件药盒 + App | 微信小程序 | App | App |
| **老人使用门槛** | 中（需学习硬件操作） | 低（微信消息提醒） | 高（需安装 App） | 高（偏专业医疗） |
| **子女远程监控** | ✅ 支持 | ❌ 没有子女端 | ❌ 不支持 | ❌ 不支持 |
| **家庭共享** | ❌ 单设备单用户 | ❌ 无家庭概念 | ❌ 无 | ❌ 无 |
| **价格** | ¥199-799 | 免费 | 免费 | 免费 |
| **提醒方式** | 药盒声光 + App 推送 | 微信订阅消息 | App 推送 | App 推送 |
| **药品录入** | 手动 | 手动 | 搜索+扫码 | 手动 |
| **余量管理** | ✅ 实时 | ❌ 无 | ❌ 无 | ❌ 无 |
| **药品数据库** | ❌ | ❌ | ✅（丰富） | ✅（专业） |
| **弱点** | 贵、需要充电、老人不爱用硬件 | 功能单一、纯工具 | 偏资讯、无家庭协同 | 偏医生端、不适合C端老人 |

### 8.2 我们的差异化定位

```
┌────────────────────────────────────────────────┐
│                                                  │
│   硬件方案        我们的位置         纯App方案     │
│   ←───────────────●──────────────────→           │
│   贵/难推广      零硬件/小程序       难/老人不用    │
│                                                  │
│   核心差异:                                       │
│   1. 小程序 = 老人零安装成本                       │
│   2. 家庭组 = 连接老人和子女两端                    │
│   3. 分级通知 = 不漏掉任何一次漏服                   │
│   4. 确认反馈 = 子女知道「吃了」而不是「提醒了」       │
│                                                  │
└────────────────────────────────────────────────┘
```

**一句话定位**：不是「提醒工具」，而是「连接老人和子女的用药安全网」。

## 9. 关键决策记录

| 编号 | 决策 | 理由 | 决策日期 |
|------|------|------|----------|
| D1 | 不做硬件，纯小程序方案 | 硬件供应链门槛高、用户接受度低、定价难 | 2026-07-06 |
| D2 | 老人端只有确认操作，不做药品管理 | 药品管理复杂度高，老人操作成本大，应交由子女代管 | 2026-07-06 |
| D3 | 分开「老人端」和「子女端」两个视图 | 两端需求完全不同：老人要简单，子女要信息密度 | 2026-07-06 |
| D4 | MVP 不做 OCR | 识别准确率风险高，MVP 先用手动+模板库验证核心价值 | 2026-07-06 |
| D5 | 优先微信订阅消息，短信/语音做兜底 | 订阅消息免费且触达率高，短信和语音有成本，按需触发 | 2026-07-06 |
| D6 | 多对多家庭组模型 | 一个老人可有多个子女监护，一个子女可监护多位老人 | 2026-07-06 |
| D7 | 老人自主确认为主，子女追问为辅 | 尊重老人自主权，降低被监视感，超时才升级通知子女 | 2026-07-06 |
| D8 | 短信兜底进 P1（Should Have），语音电话 P2（Could Have） | CEO 确认：短信作为微信消息失效后的第一道兜底，语音电话作为高危场景的第二道兜底 | 2026-07-06 |
| D9 | 药品模板库自建 + 保留第三方扩展能力 | MVP 阶段手动整理 100 种常见慢病药数据，数据模型预留第三方药品库对接字段 | 2026-07-06 |
| D10 | Web 管理后台分阶段做 | CEO 确认：先做用户端功能（小程序），Web 后台在用户功能跑通后启动 | 2026-07-06 |
| D11 | 产品名称确定为「按时吃药」 | 口语化、场景感强、两端用户都能直观理解 | 2026-07-06 |
