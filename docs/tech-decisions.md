## ADR-001: Go + Gin 作为后端框架

| 属性 | 内容 |
|------|------|
| **状态** | 已确认 |
| **决策** | Go 1.22+ + Gin 框架 |
| **背景** | CEO 指定 Go 作为后端语言，需要选择 Web 框架 |
| **选项** | A. 标准库 net/http B. Gin C. Echo D. Fiber |
| **选择** | **Gin** |
| **理由** | 1. 社区最活跃（75k+ stars），文档和案例丰富 2. 中间件生态成熟（auth/logger/ratelimit/cors 开箱即用） 3. 性能足够，Gin 路由性能比 net/http 高 10x+ 4. 上手简单，符合「成熟优先」原则 |
| **后果** | Gin 的 binding 校验需要额外注意中文错误提示定制 |

## ADR-002: GORM 作为 ORM

| 属性 | 内容 |
|------|------|
| **状态** | 已确认 |
| **决策** | GORM v2 |
| **背景** | 需要 ORM 简化数据库操作，减少 SQL 手写量 |
| **选项** | A. GORM B. sqlx C. ent |
| **选择** | **GORM** |
| **理由** | 1. Go 生态中最成熟的 ORM（36k+ stars） 2. AutoMigrate 能力方便 MVP 快速迭代 3. 支持软删除、关联查询、Hook 机制 4. 中文文档完善 |
| **后果** | 复杂查询性能不如手写 SQL，需在关键路径（定时任务扫描）使用原生 SQL |

## ADR-003: MySQL 8.0 + 逻辑外键

| 属性 | 内容 |
|------|------|
| **状态** | 已确认 |
| **决策** | MySQL 8.0，不使用物理外键约束，通过代码逻辑保证一致性 |
| **背景** | 需要关系型数据库存储用户、家庭、药品、提醒等结构化数据 |
| **选项** | A. MySQL B. PostgreSQL C. MongoDB |
| **选择** | **MySQL 8.0** |
| **理由** | 1. Go + MySQL 是微信小程序后端的经典组合 2. 腾讯云 MySQL 兼容性好，部署简单 3. 不强制物理外键：便于后续分库分表，避免外键性能损耗 4. 字符集 utf8mb4，支持 emoji |
| **后果** | 数据一致性依赖 Repository 层代码保证，需要充分的单元测试 |

## ADR-004: Redis 用于缓存 + 定时任务锁

| 属性 | 内容 |
|------|------|
| **状态** | 已确认 |
| **决策** | Redis 7.x，用于 JWT 黑名单、登录态缓存、定时任务分布式锁 |
| **背景** | 需要缓存和简单的任务队列 |
| **选项** | A. 无缓存（纯 MySQL）B. Redis C. Memcached |
| **选择** | **Redis** |
| **理由** | 1. JWT 无状态登出需要用黑名单（Redis TTL = Token 有效期） 2. 定时任务扫描需要分布式锁防重（单机部署可省略，但保留扩展能力） 3. 后续短信发送可以走 Redis 队列削峰 |
| **后果** | 增加了一个运维依赖，但 Redis 是标配级中间件 |

## ADR-005: robfig/cron 用于定时任务

| 属性 | 内容 |
|------|------|
| **状态** | 已确认 |
| **决策** | 使用 robfig/cron v3 库实现提醒调度 |
| **背景** | 需要每分钟扫描用药计划，生成当日提醒并推送 |
| **选项** | A. robfig/cron B. Linux crontab C. 外部消息队列（RabbitMQ/Kafka） |
| **选择** | **robfig/cron** |
| **理由** | 1. Go 原生实现，无需额外进程 2. 支持秒级精度（@every 60s）满足 1 分钟内推送的精度要求 3. MVP 阶段单机部署足够，后续可加 Redis 锁支持多实例 4. 简单，符合「简单优先」原则 |
| **后果** | 多实例部署时需加 Redis 分布式锁，否则会重复推送 |

## ADR-006: 微信订阅消息 + 腾讯云短信作为通知通道

| 属性 | 内容 |
|------|------|
| **状态** | 已确认 |
| **决策** | 主通道 = 微信订阅消息（免费），兜底 = 腾讯云短信（P1），语音电话（P2） |
| **背景** | 需要触达老人和子女两端 |
| **选项** | A. 仅微信订阅消息 B. 微信 + 短信 C. 微信 + 短信 + 语音 |
| **选择** | **B（P1）+ C（P2）** |
| **理由** | 1. 微信订阅消息免费且触达率最高 2. 腾讯云短信 0.045 元/条，成本可控 3. 腾讯云语音通知 0.1 元/次，需要模板审核 4. 每个外部服务封装为独立 interface，方便切换供应商 |
| **后果** | 短信需要申请腾讯云短信模板（需提前 3-5 个工作日审核） |

## ADR-007: JWT 鉴权方案

| 属性 | 内容 |
|------|------|
| **状态** | 已确认 |
| **决策** | 微信 code 换取 JWT Token，Token 有效期 7 天，Refresh Token 30 天 |
| **背景** | 小程序需要无状态鉴权 |
| **选项** | A. Session + Cookie B. JWT C. 微信 OpenID 直传 |
| **选择** | **JWT**（Access Token 7 天 + Refresh Token 30 天） |
| **理由** | 1. 小程序不支持 Cookie，JWT 更适合 2. 7 天有效期减少登录次数，降级 Token 需配合 Redis 黑名单 3. 微信 OpenID 不能直接暴露给前端作为鉴权凭据（安全风险） |
| **后果** | JWT 无法主动失效（登出），需要 Redis 维护黑名单 |

## ADR-008: 分层架构

| 属性 | 内容 |
|------|------|
| **状态** | 已确认 |
| **决策** | Handler → Service → Repository 三层架构 |
| **背景** | 需要清晰的代码组织方式 |
| **选项** | A. 扁平结构 B. 三层架构 C. DDD 六边形架构 |
| **选择** | **三层架构**（Handler / Service / Repository） |
| **理由** | 1. Go 项目最主流的分层方式 2. 职责清晰：Handler 处理 HTTP、Service 处理业务、Repository 处理数据 3. MVP 阶段不需要 DDD 的复杂度 |
| **后果** | 如果未来业务复杂（如多端多流程），可能需要引入 Domain 层 |

## ADR-009: 药品模板库数据模型预留扩展

| 属性 | 内容 |
|------|------|
| **状态** | 已确认 |
| **决策** | medicines 表预留 `external_code` 和 `external_source` 字段 |
| **背景** | CEO 要求先自建药品库，但保留对接第三方能力 |
| **选项** | A. 不自建，直接接第三方 B. 自建，不留扩展 C. 自建 + 预留扩展 |
| **选择** | **C** |
| **理由** | MVP 自己整理 100 种常见慢病药数据，数据模型加两个字段：`external_code VARCHAR(64)`（第三方药品编码）和 `external_source VARCHAR(32)`（来源标识，如 ypk/39health），后续对接第三方时只需填充这两个字段即可 |
| **后果** | 初始数据整理工作量约 2-3 天 |

## ADR-010: Web 开发阶段认证方案（双模式）

| 属性 | 内容 |
|------|------|
| **状态** | 已确认 |
| **决策** | 开发阶段使用手机号+bcrypt 密码登录；生产阶段使用微信 code 登录 |
| **背景** | 小程序未上线阶段需要 Web 页面进行后端功能验证，无法使用微信登录 |
| **选项** | A. 仅保留微信 code 登录 B. 新增用户名密码登录 C. 双模式并存 |
| **选择** | **C. 双模式并存** |
| **理由** | 1. 开发阶段 Web 页面通过 `POST /auth/register` + `POST /auth/login-password` 完成注册登录 2. 密码使用 bcrypt 哈希存储到 `users.password_hash` 字段 3. 生产环境微信 code 登录走原有 `POST /auth/login`（code2session → openid → JWT）4. 两套逻辑共享同一 `generateTokenPair` 方法，避免重复代码 5. 小程序上线后 `/register` 和 `/login-password` 可废弃，`password_hash` 字段保留不影响 |
| **后果** | `users` 表新增 `password_hash` 字段；AuthService 新增 `RegisterByPassword` 和 `LoginByPassword` 方法 |
