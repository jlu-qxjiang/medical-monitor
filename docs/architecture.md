## 6. 关键技术难点

### 5.1 提醒调度的并发模型

**挑战:**
- 每个用户可能有 3-5 个用药时间点
- 1000 个用户 × 3 个时间点 = 3000 条提醒/天
- 需要在 ±1 分钟内准时生成并推送

**方案:**
```
reminder_scheduler（每分钟执行一次）:

1. 获取 Redis 分布式锁 (key: "scheduler:reminder", TTL 50s)
2. 查询 medicine_schedules WHERE time_of_day BETWEEN (NOW() - 1min) AND (NOW() + 1min) AND is_active = 1
3. 对每条 schedule:
   a. 检查是否已生成今日提醒 (reminders WHERE schedule_id + remind_date = today)
   b. 未生成 → 创建 reminder + reminder_items（快照药品信息）
   c. 已生成 → 跳过
4. 查询 reminders WHERE remind_time <= NOW() AND status = 'pending'
5. 对每条 reminder → 调用微信订阅消息推送 → status = 'sent'
6. 释放锁
```

**性能计算:**
- 1000 个用户，单次扫描 < 500ms
- 微信消息推送并发控制在 50 QPS（微信限制），使用 rate limiter

---

### 5.2 微信订阅消息频率限制

**限制:** 微信订阅消息对同一用户同一模板有频次限制，且用户每次授权只能用有限次数。

**应对策略:**

| 策略 | 说明 |
|------|------|
| **精准推送** | 仅在用药时间点推送，不滥用 |
| **合并推送** | 同一时间点的多种药品合并为一条消息 |
| **授权引导** | 子女端显示「老人订阅状态」，过期前 3 天引导重新授权 |
| **兜底通道** | 微信消息失败 → 短信（P1）→ 语音电话（P2） |
| **静默检测** | 每晚 22:00 巡检当日授权状态，异常通知子女 |

### 5.3 数据脱敏方案

```
脱敏层级:

1. API 响应层（Middleware 自动处理）:
   - phone: "138****1234"（log 中自动替换）
   - 不做额外处理即返回，Service 层返回完整数据

2. 数据库存储层:
   - phone: 仅存后 4 位（phone 字段）
   - phone_enc: AES-256-GCM 密文存储完整手机号
   - openid: 不通过 API 返回，仅在内部使用

3. 日志层:
   - zap 自定义 Encoder，自动脱敏手机号/身份证字段
   - JSON 类型的请求体自动扫描并替换敏感 key

4. 审计日志:
   - audit_logs.detail 中敏感字段写入前替换为 "***"
```

### 5.4 提醒生成与跨天边界

**边界场景:**
- 用药计划 23:30 → 提醒生成时间在当天 23:30
- 凌晨 00:30 的提醒 → 属于新的一天

**方案:**
- reminders 按 `remind_date` 分区查询
- scheduler 每次执行时，以当前时间的日期为基准，扫描 ±1min 窗口
- 跨天时（23:59 → 00:01），自动生成新一天的提醒

## 7. 安全方案

### 7.1 认证流程

```
用户点击微信登录
  → 小程序调用 wx.login() 获取 code
  → POST /api/v1/auth/login { code }
  → 后端用 code 换取 openid + session_key（微信接口）
  → 查找或创建用户
  → 生成 JWT Token (sub=user_id, exp=7天)
  → 返回 access_token + refresh_token
```

### 7.2 鉴权机制

```
中间件 auth.go:
  1. 提取 Authorization header
  2. 解析 JWT → 提取 user_id
  3. 验证 Token 是否在 Redis 黑名单中
  4. Context.Set("user_id", user_id)
  5. 后续 Handler/Service 从 Context 获取当前用户

中间件 family.go:
  1. 从 URL 提取 family_id
  2. 查询 family_members WHERE family_id = ? AND user_id = ?
  3. 不存在 → 403 非家庭成员

中间件 role.go:
  1. 查询当前用户在家庭组中的角色
  2. elder 角色调用管理类接口（药品/计划增删改）→ 403
```

### 7.3 数据加密

| 数据 | 加密方式 | 密钥管理 |
|------|----------|----------|
| 手机号完整值 | AES-256-GCM | 环境变量 `ENCRYPTION_KEY`，定期轮换 |
| JWT 签名 | HMAC-SHA256 | 环境变量 `JWT_SECRET` |
| 数据库连接 | TLS | 腾讯云 MySQL 自动启用 |

### 7.4 API 限流

| 接口类型 | 限制 | 窗口 | 说明 |
|----------|------|------|------|
| 登录 | 10 次 | 1 分钟 | 防止恶意调用 |
| 通用接口 | 100 次 | 1 分钟 | 单用户 |
| 确认接口 | 30 次 | 1 分钟 | 防止重复提交 |
| 定时任务推送 | 50 次 | 1 秒 | 微信 API 限制 |

## 8. 关键风险点（供王测试重点测试）

| 编号 | 风险 | 等级 | 测试重点 |
|------|------|------|----------|
| R1 | 提醒重复推送（无分布式锁） | 高 | 多实例下同一提醒是否只推送一次 |
| R2 | 跨天提醒边界 | 高 | 23:59 和 00:01 的提醒正确性 |
| R3 | 确认后余量未扣减 | 高 | 确认 → 查询余量 → 确认 → 再次查询 |
| R4 | JWT 过期处理 | 中 | Token 过期后前端行为是否正确 |
| R5 | 微信消息推送失败重试 | 中 | 模拟微信 API 返回错误 → 重试机制 |
| R6 | 并发确认同一条提醒 | 中 | 两人同时点「已服用」→ 幂等处理 |
| R7 | 药品删除后历史记录完整性 | 中 | 删除药品 → 历史提醒中的药品名快照是否完整 |
| R8 | 短信发送频率控制 | 中 | 短时间内多条超时提醒 → 不重复发短信 |
