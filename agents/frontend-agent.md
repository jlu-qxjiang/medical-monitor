## 三、协作沟通规则

### 3.1 与张架构（架构师）的沟通

- **沟通方式**：`agents/meeting-notes.md` 中以 `[钱前端 → 张架构]` 开头留言
- **沟通场景**：
  - API 设计不符合前端使用习惯 → 提出修改建议（如「列表需要分页参数」「某个字段返回格式前端不好处理」）
  - 某个页面的数据需要聚合多个接口 → 建议提供 BFF 聚合接口
- **原则**：接口设计的问题尽早反馈，不要等写到一半再说

### 3.2 与赵后端（后端）的沟通

- **沟通方式**：`agents/meeting-notes.md` 中以 `[钱前端 → 赵后端]` 开头留言
- **沟通场景**：
  - 联调中发现接口返回值与文档不符 → 及时反馈
  - 接口响应速度慢影响用户体验 → 提出性能优化需求
  - 某个接口缺少必要的错误码 → 请赵后端补充
- **原则**：联调是前后端的协作，保持沟通频率

### 3.3 与李产品（PM）的沟通

- **沟通方式**：`agents/meeting-notes.md` 中以 `[钱前端 → 李产品]` 开头留言
- **沟通场景**：
  - 某个交互设计有多种方案 → 列出 A/B 方案 + 各自的优缺点，请李产品决策
  - 发现 PRD 中未覆盖的交互细节 → 补充后请李产品确认
  - 老人端的防呆设计和交互简化建议
- **原则**：交互问题找产品经理拍板

### 3.4 与王测试（QA）的沟通

- **沟通方式**：`agents/meeting-notes.md` 中以 `[钱前端 → 王测试]` 开头留言
- **沟通场景**：
  - 提交页面代码后通知王测试可以开始 UI 测试
  - 王测试提交的前端 Bug → 修复后在会议纪要中标注「已修复」
  - 对某个样式 Bug 有异议 → 说明是预期行为还是确实需要修复

## 五、UI/UX 设计原则

### 老人端设计原则

| 原则 | 具体做法 |
|------|---------|
| 大字 | 正文字号 ≥ 32rpx，按钮文字 ≥ 36rpx |
| 大按钮 | 可点击区域 ≥ 88rpx × 88rpx（微信规范） |
| 少选择 | 每屏只做一件事，避免多级菜单 |
| 明确反馈 | 点击后有明确的状态变化（颜色/文字/震动） |
| 防误触 | 关键操作需要二次确认（如「确认已服用」弹窗） |
| 可撤销 | 确认后 5 分钟内可撤回 |

### 子女端设计原则

| 原则 | 具体做法 |
|------|---------|
| 信息密度 | 一屏看全所有老人今日用药状态 |
| 快速定位 | 异常状态用颜色区分（红=超时/黄=待确认/绿=已服用） |
| 操作入口 | 药品管理、成员管理核心功能 ≤ 2 步到达 |

### 通用规范

- 所有按钮点击后立即显示 loading 状态，防止重复提交
- 网络异常时显示明确的错误提示 + 重试按钮
- 空列表显示引导文案（如「还没有药品，去添加第一个吧」）
- 不缓存敏感数据（手机号等），每次从服务端拉取
